# hcc-orchestrator-agent-dev

Rehor bot instance for HCC.

## Setup

```bash
git clone --recurse-submodules <this-repo-url>
cd hcc-orchestrator-agent-dev
```

## Submodule Update

```bash
git submodule update --remote dev-bot
git add dev-bot
git commit -m "chore: bump dev-bot submodule"
```

## Build

Builds are handled by Konflux CI. The `.tekton/` pipeline files are generated by the
Konflux UI after Component registration. The Dockerfile is at `dev-bot/Dockerfile.runner`.

## Clowder V2 migrations

Tickets involving Clowder dependency endpoints or Clowder migrations use a gated
two-persona workflow:

1. Add `hcc-ai-orchestrator`, `repo:<name>`, and
   `persona:clowder-v2-assessment`. The assessment persona is read-only and produces
   either a verified migration packet or a Jira checklist of unresolved decisions.
2. Use `persona:clowder-v2-migration` only after the packet has no fields marked
   `Decision required`. The migration persona implements and tests the packet rather
   than guessing missing endpoint, authentication, TLS, fallback, or workload details.

The service-discovery scope is limited to RBAC, Kessel, Export service, and Sources
clients that already use the Clowder endpoint API. Environment/config-only discovery
is not converted to Clowder by this workflow. For `ClowdAppRef` provisioning or
cutover tickets, also follow
[`personas/clowder-v2/provisioning.md`](instance/hcc-orchestrator-config/agent/personas/clowder-v2/provisioning.md).

The deterministic assessment can also be run directly against a target checkout:

```bash
python3 instance/hcc-orchestrator-config/agent/skills/clowder-v2-assess/scripts/assess.py \
  --repo <target-repo> --phase before
```

Run it again with `--phase after` after migration. The complete assessment and
implementation contracts live in
[`clowder-v2-assessment`](instance/hcc-orchestrator-config/agent/personas/clowder-v2-assessment/prompt.md)
and
[`clowder-v2-migration`](instance/hcc-orchestrator-config/agent/personas/clowder-v2-migration/prompt.md).

## Cross-service scans (how to tag work)

This instance can run a **cross-service analysis** — you define *what* to analyze in a
Jira epic; the bot fans it out one service per cycle, aggregates the findings, and
(after you approve) generates implementation tickets. Full design: [`docs/scan-workflow.md`](docs/scan-workflow.md).

**`hcc-ai-orchestrator` is the bot pickup label — every ticket the bot should touch
must carry it.** The other labels below decide what the bot *does* with a ticket.

### 1. Kick off a scan
Create an **epic** in the bot's Jira project:
- **Summary + description:** state the focus — the exact question(s) to answer for each
  service (be specific; add search terms / a definition of "done" if you can).
- **Labels:** `hcc-ai-orchestrator` **+** `hcc-scan`.
- **Optional — choose which services to scan.** Default (no scope given) is **all**
  ~37 services in the registry. Narrow it in one of two ways:
  - **By group — add a label to the epic:** `group:tenant` **or** `group:platform`
    (Jira labels, same place you added the two above).
  - **By explicit list — add a line to the epic *description*:** a line beginning
    `Services:` followed by comma-separated registry repo names, e.g.

    ```
    Services: advisor-backend, patchman-engine, ros-backend
    ```

    If both a `group:` label and a `Services:` line are present, the explicit list
    wins (intersected with the registry). Names must match `repo` values in the
    registry (see the list command at the bottom).
- **Adding context / reference material.** The bot reads **ticket text** and **Jira
  attachments** only — it has **no web access**, so a pasted Google Doc / Drive /
  external link is *not* fetchable. Put the material where the bot can see it:
  - paste it directly into the epic **description** or a **comment**, or
  - **attach the file** to the epic (spec, CSV of targets, reference doc).

  Anything on the epic flows into every per-service analysis automatically.

### 2. Let it analyze (no action)
The bot runs `/plan-scan` → one analysis child per service
(`hcc-ai-orchestrator` + `needs-investigation` + `repo:<name>` + `scan:<EPIC-KEY>`),
then works each child read-only via the `analyst` persona, posting a per-service
verdict + `file:line` evidence to that child ticket.

### 2b. Aggregate to the epic (one action)
Aggregation is **human-triggered** — the bot does not roll findings up on its own.
When the child analyses look done, add the **`scan-aggregate`** label to the epic and
move it back into the pickup queue (a pickup status such as *To Do*, assignee empty —
an *In Progress* epic won't be re-picked-up). The bot runs `/aggregate-scan`, posts
the epic-level findings table (per-service rows + common patterns + follow-ups), and
removes the `scan-aggregate` label. Re-add it anytime to refresh (e.g. after an
expansion adds services).

### Expanding a scan (grow one epic)
Start narrow, prove the focus, then widen **the same epic** — no need to file a new one.
Edit the epic's scope (broaden the `Services:` line, swap to a broader `group:` label,
or remove the scope entirely for all ~37) and **re-trigger the epic** (move it back into
the bot's pickup queue — the same status / no-assignee state it started in). `/plan-scan`
runs **additively**: it creates analysis children only for the newly in-scope services
and leaves the existing analyses (and their results) untouched. Re-triggering with no
scope change is a safe no-op. Once the new analyses finish, re-add **`scan-aggregate`**
(step 2b) to refresh the epic's table with the added services.

### 3. Approve implementation
Review the epic's aggregated table. To turn follow-ups into work, add **`impl-approved`**
to the epic. The bot runs `/generate-impl-tickets` → `hcc-ai-orchestrator` + `hcc-impl`
+ `repo:<name>` tickets (no `needs-investigation`), which flow through the normal
implement→PR loop with the `backend`/`frontend` persona. Then review the PRs.

### Label cheat-sheet
| Ticket | Labels |
|---|---|
| Scan epic | `hcc-ai-orchestrator` `hcc-scan` (+ optional `group:tenant`\|`group:platform` label, or a `Services: a, b, c` line in the description) |
| Analysis child (bot-created) | `hcc-ai-orchestrator` `needs-investigation` `repo:<name>` `scan:<EPIC-KEY>` |
| Aggregate trigger | add `scan-aggregate` to the epic (bot removes it after posting) |
| Approval | add `impl-approved` to the epic |
| Impl ticket (bot-created) | `hcc-ai-orchestrator` `hcc-impl` `repo:<name>` |

**Re-triggering an epic** (to aggregate, expand scope, or approve) requires the epic to
be back in a **pickup status** (e.g. *To Do*) with **assignee empty** — the bot does not
re-pick-up an *In Progress* epic. Adding a label alone is not enough.

Extra: `persona:<name>` on any ticket forces a specific persona. One-off read-only
investigation (no scan): `hcc-ai-orchestrator` + `needs-investigation` + `repo:<name>`.

### Editing the target catalog
Services and their `group` (platform/tenant) live in
`instance/hcc-orchestrator-config/agent/skills/service-registry/registry.json`. List
them with:
```bash
python3 instance/hcc-orchestrator-config/agent/skills/service-registry/registry.py list --group all
```
